# 班表載入效能驗證

驗證日期：2026/09/24。測量使用既有真實班表，轉換過程未呼叫 TDX。程式與資料尚未發布。

## 原因與處理

原本每個日期檔同時包含前日、當日、隔日的全台台鐵及高鐵。相鄰檔案重複保存兩天資料，切換篩選也重新讀檔；畫面執行緒解析及驗證後，再把整份資料複製至新建的背景工作。

調整後，日期檔只保留狀態及資料位置。班表依日期分成周邊台鐵、全台台鐵、高鐵三類，站碼及車種使用字典，時間存為相鄰停靠站的差值；還原保留原始精度，不更改發車或到站時間。只有周邊查詢會裁掉路線外站點，全台台鐵檔保留完整列車資料。

依路線載入所需類別，前日、當日、隔日資料仍齊備。背景工作持續運作，負責下載、解析及計算，畫面只接收行程與更新狀態。相鄰日期共用資料；同日調整篩選不重抓已讀取的班表。更新後檔案雜湊改變，取得時間與失敗標記則獨立保存。

機捷保留所有經 A18 的雙向車站查詢，移除不用的多語站名、欄位及非 A18 的 OD 旅行時間，檔案由 1,091,367 bytes 降為 493,450 bytes。下載後同樣可共用，不因切換日期重抓整份。

## 檔案大小

使用 2026/09/25 班表。單位為十進位 KB、MB；每種查詢包含日期索引及三天銜接資料。下表 gzip 使用 Node.js `gzipSync` 預設設定，以同一方式比較前後大小。

| 查詢範圍 | 原始 JSON 大小 | gzip 大小 |
| --- | ---: | ---: |
| 修改前，所有查詢皆載入同一檔 | 5,468,956 bytes | 590,481 bytes |
| 修改後，內灣／新竹周邊 | 42,383 bytes | 6,685 bytes |
| 修改後，全台台鐵 | 720,711 bytes | 111,681 bytes |
| 修改後，周邊台鐵＋高鐵 | 97,040 bytes | 12,842 bytes |

正式站於本次量測使用 gzip，實際下載舊版 2026/09/25 班表為 604,582 bytes，約 1.22 秒；服務端壓縮設定與本機 gzip 不同，所以不直接混用作縮減比例。原始 JSON 的 5.47 MB 並非該次實際網路流量。

從 9/25 切至 9/26 時，可沿用 9/25、9/26 兩份周邊班表，只新增 9/26 的索引和 9/27 的班表，共 14,685 bytes，gzip 約 2,524 bytes。記憶體快取有上限，淘汰後可由瀏覽器 HTTP 快取讀取內容雜湊相同的檔案。

## 正確性與瀏覽器驗證

- 65 項單元測試通過：格式往返還原、跨日與秒數、車種、快取共用、更新與失敗重試、原始取得時間、每日只補新增高鐵日期及既有轉乘規則。
- 手機／桌面共 46 項操作測試通過。一般操作以新格式測試，部分既有轉乘案例保留舊格式，兼顧過渡相容；另驗證慢速舊查詢不覆蓋最後選定日期。
- 以轉換前後的 9/25 真實班表比對 562 組查詢，行程一致：周邊所有起迄站組合及三種篩選，另包含雙向台鐵、高鐵及機捷路線。
- 全台台鐵及高鐵壓縮檔還原後，列車、停靠站與各欄位和原始資料完全一致。另比對機捷所有站往返 A18 的平日、國定假日及週末班次，結果一致。
- TypeScript 檢查與 `BASE_PATH=/neiwan-line/ npm run build` 通過。
- 以本機正式建置、真實班表與 Chromium 查詢，9/26 → 9/27 → 9/26 分別約 31、30、29 毫秒；新增日期只有索引及一個周邊檔案請求，已看過的日期為零新增班表請求。瀏覽器無錯誤。此數字包含本機操作及顯示等待，不代表正式站網路速度。

## 更新與發布

`npm run data:generate` 直接輸出新格式。`public/data/slices/index.json` 保存可還原的全台台鐵及高鐵資料位置、原始取得時間和失敗狀態，每日排程仍沿用已取得高鐵日期，僅補缺漏或新增日期。

既有檔案可執行 `npm run data:compact` 離線轉換，不需要 TDX 憑證。發布時須一起帶上程式碼、日期索引及整個 `public/data/slices/`。現有 GitHub Actions 已使用 `git add public/data` 與完整建置，不需新增秘密金鑰或改變排程。
