# 機捷更新與改班核實

機捷更新先保存原始來源，再分別判斷資料完整性與班表異動。資料一致時，以最新現行班表為主；增減班、首末班調整及停站變更自動採用，差異保留在報告中。核實紀錄不會略過資料完整性檢查。

## 更新結果

- `accepted`：資料一致、服務完整，且沒有需核對的異動，或異動已按精確來源版本核實。
- `scheduled`：已取得有明確生效日的未來班表，保留現行版本，依營運日切換。
- `needs-review`：新來源本身仍有結構矛盾，需要沿用舊人工修正，且修正後服務與已核實版本不同。保留先前資料，需核對新的停站定義。
- `invalid`：缺站、方向矛盾、引用不存在的停靠模式、起站或終點不在停靠模式、時間不合法、缺少旅行時間等，拒絕發布。
- `fetch-failed`：尚未完成來源取得或讀取作業，保留上次資料並記錄錯誤。

每個日期會比較所有車站與 A18 之間雙向服務；兩份資料只有在該日期都適用時才比較班數。減班超過 30% 或首末班變動至少 60 分鐘會產生報告，不阻擋發布。行駛規則明確排除當日，或車站列明確提供空班次時，不補回舊班次；整站缺漏、整份沒有任何班次仍視為資料不完整，不能推定停駛。

## 核實並接受正式改班

1. 在 GitHub Actions 的更新執行頁閱讀「機捷更新」摘要，下載 `metro-update-report` 附件（保存 30 天）。內容含 `candidate.raw.json`、`report.json`、`summary.md`；成功時另有精簡後的 `candidate.json`。
2. 對照桃捷官方時刻表／公告，確認適用起訖日期、受影響日期、方向、首末班、普通／直達／跳站的實際停站。多次下載相同資料本身不算官方佐證。
3. 在 `scripts/metro-reviews.json` 增加該來源 `sourceHash` 的核實紀錄，填 `reviewedAt`、`reason`、官方 HTTPS `sources` 及 `validity.from/through`。資料指紋忽略 API 刷新時間、版本流水號與陣列順序，但包含所有班表、停站及抵達時間內容。來源內容變動後，不能直接以舊紀錄核准整份新班表；限定欄位修正的沿用條件見下方。
4. 若原始欄位互相矛盾，只能附上已核實的限定班次修正：使用起站、方向、整列目的地、平假日標籤、原發車時間、原車種與原停靠模式唯一對應；可補停靠模式、每班終點、專屬旅行時間與乘客可讀名稱。不能新增或改寫發車時間。新模式需附官方停站依據。
5. 跑單元測試與建置、提交核實紀錄，重新執行每日更新。沒有對所有未來版本放行的環境變數或全域略過開關。

TDX 若省略 `Direction`，本站只在機捷已知線形上能由明確起迄站唯一確認方向時補入；明確填錯的方向仍會被攔截。其他缺漏不以猜測補齊。

## 日期與舊資料

- 已知適用期間只服務該期間的營運日。未來版本不提前啟用，較新版本到期後不會復活舊版。
- 改班時保留必要的前一營運日，以處理午夜後末班車。更新失敗不改寫原取得時間。
- 未知適用期可依常態規則推估查詢範圍，但超過 **七個實際日**未取得新資料就停止提供機捷行程；此期限不是把未來查詢範圍縮成七天。
- 現行來源未提供日期時，服務與今日已核實版本相同才沿用原有效期間；服務變更則自本地採用日 `effectiveFrom` 起使用新資料，不繼承舊效期。未來查詢依行駛規則推算，仍適用七天未更新期限。保留前一營運日版本及另存的未來正式班表；過期或尚未生效版本不能提供效期依據。
- A18 與高鐵桃園的單純步行接駁不依賴機捷班表。

## 來源格式改變與服務等價

完整來源先通過結構與服務完整性檢查，再比對本站使用的 A18 往返服務。比較每班的起站、方向、各星期／國定假日行駛規則、發車時間、車種、從起站至終點的實際停站，以及各可查詢目的地的旅行時間。拆列、合列、列順序、模式代碼及顯示名稱不影響結果；重複班次保留數量，不透過查詢引擎去重或僅抽查幾天。

先前版本保留的是 A18 接駁所需資料，因此等價判斷只涵蓋本站使用範圍，不宣稱整條機捷所有行程完全相同。其他站的完整原始資料仍須先通過檢查。

已核實的每班專屬旅行時間獨立於來源列分組：只有行駛日、時間、車種、方向、起終點及停站唯一匹配，且原始旅行時間未變時才沿用。來源若提供衝突的專屬旅行時間就不覆寫。新版基礎旅行時間即使被補正值覆蓋，也列入比較，避免隱藏上游異動。核實補正及效期只從今日仍適用的版本取得。

官方核實過的停靠模式／終點修正，可附 `sourcePatterns` 保存當時原始停站定義。來源指紋變動時，只有修正紀錄仍在效期內、涵蓋現行版本期間、原始模式定義及班次選擇條件唯一吻合、修正後的模式定義也吻合，才可嘗試修正。明確的新每班終點衝突不覆寫。這個步驟不授予新效期，修正後仍須通過完整性檢查與整體 A18 服務等價比對；任何實際改班都不會因此放行。

原始 `sourceHash` 繼續用於追查與限定欄位修正；不再把整份來源指紋不同直接視為改班。`report.json` 的 `equivalence` 保存比對結果、原有效期間、沿用專屬旅行時間筆數及完整增刪差異；摘要顯示部分差異。無日期的現行新版本若結構完整且服務有變動，採用新服務並保存完整差異；若仍需舊結構修正，則必須所有服務記錄相同才接受。

2026-10-16 的兩次來源分別為新版 174 列班次，以及舊版 128 列班次搭配新版 6 個停靠模式。後者班次與旅行時間仍與 10/15 原始來源相同，差異為 SP5 的路線代碼及新增 SP6 定義。以上兩種組合均透過相同的逐班條件與完整服務比對處理，不增加新的整份來源核准紀錄。

## 2026-10-30 更新策略調整

正常改班以新資料為主，完整服務比對用於差異報告及限制舊修正的沿用，不再要求所有新版本與舊班表相同。來源結構已一致時不嘗試舊停站／終點修正；只有來源仍無法解讀時才嘗試核實修正，且必須整體服務相同才接受。
